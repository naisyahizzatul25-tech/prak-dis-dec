### 4.1.2 Persiapan File Konfigurasi

#### Langkah 1: Membuat Direktori Kerja

<img src="img/4.1.2-langkah1.png" width="800" />

* **Pembahasan Detail:**
  Perintah `mkdir -p streaming-replication && cd streaming-replication` dieksekusi pada lingkungan shell Bash.
  * Bendera `-p` (*parents*) pada perintah `mkdir` memastikan bahwa sistem operasi akan membuat direktori bernama `streaming-replication` secara aman tanpa mengeluarkan pesan galat jika direktori tersebut sudah ada sebelumnya di dalam sistem berkas.
  * Perintah `cd` (*change directory*) dilanjutkan untuk memindahkan direktori kerja aktif terminal ke dalam folder baru tersebut.
  * **Analisis Kritis:** Pengisolasian ruang kerja ini merupakan praktik terbaik (*best practice*) dalam manajemen proyek terdistribusi. Langkah ini memastikan seluruh berkas manifes konfigurasional (`00_init.sql`, `01_hba.sh`, `docker-compose.yaml`, dan `env.sh`) terisolasi penuh, mencegah bentrokan nama berkas dengan modul praktikum lain, serta memudahkan proses *clean-up* atau migrasi repositori.

#### Langkah 2: Script Inisialisasi Primary (`00_init.sql`)

<img src="img/4.1.2-langkah2.png" width="800" />

* **Pembahasan Detail:**
  Menggunakan teknik *Here-Document* (`cat << 'EOF' > 00_init.sql`), sebuah berkas skrip SQL inisialisasi dibuat secara otomatis. Skrip ini akan dimasukkan ke dalam folder bootstrap PostgreSQL agar dieksekusi pada saat kontainer primary pertama kali dibuat.
  1. `CREATE USER replicator WITH REPLICATION ENCRYPTED PASSWORD 'replicator_password';`: Instuktor SQL ini berfungsi mendaftarkan peranan (*role*) pengguna sistem bernama `replicator`. Pemberian klausula `WITH REPLICATION` memberi hak akses khusus pada tingkatan engine agar pengguna ini dapat membuka koneksi socket streaming WAL. Kata sandi dienkripsi menggunakan standar keamanan `scram-sha-256`.
  2. `SELECT pg_create_physical_replication_slot('replication_slot');`: Fungsi internal PostgreSQL ini dipanggil untuk mengalokasikan satu slot replikasi fisik bernama `replication_slot`.
  * **Analisis Kritis:** Kehadiran slot replikasi fisik merupakan elemen krusial pada arsitektur streaming. Tanpa slot ini, jika node replica mengalami gangguan koneksi jaringan sementara, node primary dapat secara tidak sengaja menghapus berkas WAL yang dianggap sudah tua dari disk (`pg_wal`). Akibatnya, saat replica kembali *online*, proses sinkronisasi akan gagal total (*WAL segment already removed*) dan membutuhkan proses re-backup dari awal.

#### Langkah 3: Konfigurasi Otentikasi (`01_hba.sh`)

<img src="img/4.1.2-langkah3.png" width="800" />

* **Pembahasan Detail:**
  Berkas `01_hba.sh` disiapkan sebagai skrip Bash otomatisasi konfigurasi lapisan keamanan jaringan PostgreSQL (*Host-Based Authentication*).
  * Baris perintah `echo "host replication replicator all scram-sha-256" >> "$PGDATA/pg_hba.conf"` mengeksekusi penambahan baris aturan baru ke dalam berkas `pg_hba.conf` yang berlokasi di dalam direktori data PostgreSQL (`$PGDATA`).
  * Maksud dari aturan ini: Mengizinkan tipe koneksi `host` khusus untuk protokol `replication`, menggunakan nama pengguna `replicator`, dari sembarang alamat IP asal (`all`), dengan syarat wajib melewati tantangan enkripsi `scram-sha-256`.
  * Perintah `chmod +x 01_hba.sh` mengeksekusi modifikasi mode hak akses berkas agar memiliki atribut *executable* (`+x`).
  * **Analisis Kritis:** PostgreSQL menerapkan model keamanan *default* yang sangat ketat di mana koneksi luar untuk keperluan replikasi ditolak secara baku. Tanpa injeksi aturan ini ke dalam `pg_hba.conf`, kontainer replica tidak akan pernah diizinkan melakukan *handshake* jaringan ke primary, dan akan selalu menghasilkan pesan kesalahan *FATAL: no pg_hba.conf entry for replication connection*.

#### Langkah 4: File Docker Compose (`docker-compose.yaml`)

<img src="img/4.1.2-langkah4.png" width="800" />

* **Pembahasan Detail:**
  Berkas `docker-compose.yaml` mendefinisikan arsitektur multi-kontainer terdistribusi menggunakan citra resmi `postgres:18.3-alpine3.23`.
  * **Struktur Anchor `x-postgres-common`:** Digunakan untuk meminimalisir redundansi kode YAML. Menentukan `user: postgres`, restart policy `always`, serta mekanisme `healthcheck` berbasis perintah `pg_isready -U zuser -d zdb` yang berjalan setiap 10 detik.
  * **Service `postgres_primary`:** Ditempatkan pada port host `5432`. Melalui parameter `command`, mesin primary diinstruksikan mengaktifkan `wal_level=replica` (menghasilkan log WAL berdetail tinggi), `hot_standby=on` (mengizinkan koneksi kueri pada standby), `max_wal_senders=10` (membuka hingga 10 saluran streaming paralel), dan `hot_standby_feedback=on` (mengirimkan informasi kueri dari replica ke primary agar baris data yang sedang dibaca di replica tidak dihapus oleh proses VACUUM di primary).
  * **Service `postgres_replica`:** Ditempatkan pada port host `5433`. Kontainer ini mengimplementasikan skrip pengulang (*retry loop*) Bash dinamis:
    `until pg_basebackup --pgdata=/var/lib/postgresql/18/docker -R --slot=replication_slot --host=postgres_primary --port=5432 -U replicator -X stream; do ... done`
  * **Analisis Kritis:** Opsi `-R` pada perintah `pg_basebackup` sangat penting karena perintah ini secara otomatis menyusun berkas `standby.signal` dan menginjeksikan konfigurasi `primary_conninfo` di dalam direktori data replica. Hal ini membuat PostgreSQL replica secara otomatis mengetahui bahwa dirinya harus berjalan sebagai node *Standby Read-Only* begitu proses *booting* selesai.

#### Langkah 5: Membuat Alias Shell (`env.sh`)

<img src="img/4.1.2-langkah5.png" width="800" />

* **Pembahasan Detail:**
  Berkas `env.sh` disusun sebagai instrumen pembantu operasional (*developer productivity tool*) guna menyederhanakan sintaks perintah Docker CLI yang panjang menjadi singkatan singkat (*alias*):
  * `alias dcu="docker compose up -d"`: Menyalakan seluruh tumpukan kontainer dalam mode terisolasi di latar belakang (*detached mode*).
  * `alias dcd="docker compose down"`: Menghentikan dan menghapus kontainer, jaringan, serta volume ephemeral.
  * `alias dps="docker ps"`: Menyajikan daftar status operasional kontainer aktif.
  * `alias dep="..."` dan `der="..."`: Perintah rute cepat untuk membuka terminal tty interaktif (`docker exec -it`) langsung ke dalam sistem operasi kontainer primary atau replica.
  * `alias dlp="..."` dan `dlr="..."`: Membuka pemantauan log aktivitas streaming sistem (`docker logs`) dari masing-masing node.
  * **Analisis Kritis:** Penggunaan berkas alias ini tidak hanya mempercepat proses eksekusi pengujian, namun juga meminimalisir risiko kesalahan ketik (*human error*) saat harus berpindah-pindah konteks antara node primary dan node replica.

### 4.1.4 Verifikasi & Pengujian Streaming Replication

#### Langkah 1 & 2: Masuk ke Primary dan Cek Status Replikasi

<img src="img/4.1.4-langkah2.png" width="800" />

* **Pembahasan Detail:**
  Melalui perintah alias `dep`, terminal interaktif di dalam kontainer primary diakses. Untuk memverifikasi keaktifan sesi streaming secara ilmiah, dieksekusi kueri sistem:
  `psql -U zuser -d zdb -c "SELECT client_addr, state, sync_state FROM pg_stat_replication;"`
  * Keluaran terminal mengembalikan tabel statistik sistem dengan satu baris aktif:
    * `client_addr = 172.18.0.3`: Alamat IP virtual internal milik kontainer replica dalam jaringan Docker.
    * `state = streaming`: Menandakan proses transmisi log WAL secara fisik sedang berlangsung aktif tanpa ada hambatan.
    * `sync_state = async`: Mengonfirmasi bahwa mode replikasi yang terpasang adalah *asynchronous*.
  * **Analisis Kritis:** Mode *asynchronous* berarti node primary akan langsung mengonfirmasi transaksi `COMMIT` kepada aplikasi pengirim tanpa harus menunggu konfirmasi balasan (*acknowledgement*) dari node replica. Mode ini memberikan performa penulisan data yang sangat tinggi pada primary dengan risiko keterlambatan data (*replication lag*) sebesar beberapa milidetik pada replica.

#### Langkah 3 & 4: Masuk ke Primary dan Tambahkan Data Baru

<img src="img/4.1.4-langkah4.png" width="800" />

* **Pembahasan Detail:**
  Skenario pengujian propagasi data diawali dari node primary.
  1. Perintah `CREATE TABLE tes_replikasi (id SERIAL PRIMARY KEY, nama VARCHAR(50));` dieksekusi untuk membuat struktur tabel baru.
  2. Perintah `INSERT INTO tes_replikasi (nama) VALUES ('Data Pertama'), ('Data Kedua');` dieksekusi untuk menyisipkan dua record data.
  * Respon terminal mengembalikan pesan konfirmasi `CREATE TABLE` dan `INSERT 0 2`.
  * **Analisis Kritis:** Saat transaksi ini di-commit pada primary, PostgreSQL secara otomatis mencatat alokasi halaman tabel baru beserta baris datanya ke dalam log WAL fisik. Saluran *WAL Sender Process* pada primary secara instan mendeteksi perubahan LSN ini dan memancarkannya melalui jaringan ke node replica.

#### Langkah 5: Masuk ke Replica dan Verifikasi Data Ter-replikasi

<img src="img/4.1.4-langkah5.png" width="800" />

* **Pembahasan Detail:**
  Guna memverifikasi apakah data berhasil diterima, akses shell dipindahkan ke kontainer replica melalui perintah `der`. Kueri pembacaan dieksekusi: `psql -U zuser -d zdb -c "SELECT * FROM tes_replikasi;"`.
  * Hasil keluaran menyajikan tabel dengan data yang presisi:
    * `id = 1 | nama = Data Pertama`
    * `id = 2 | nama = Data Kedua`
  * **Analisis Kritis:** Keberhasilan kueri ini membuktikan efektivitas mekanis *Streaming Replication*. Tanpa ada intervensi kueri penulisan manual di node replica, seluruh perubahan berkas data fisik dari primary mampu diaplikasikan ulang (*replay WAL*) oleh proses *WAL Receiver* di replica dalam hitungan milidetik secara transparan.

#### Langkah 6: Uji Sifat Read-Only pada Node Replica

<img src="img/4.1.4-langkah6.png" width="800" />

* **Pembahasan Detail:**
  Guna menguji batasan aksesibilitas node standby, dilakukan pengujian batas (*edge case*) dengan mencoba mengeksekusi transaksi penulisan secara langsung pada node replica:
  `psql -U zuser -d zdb -c "INSERT INTO tes_replikasi (nama) VALUES ('Data Tiga');"`
  * Engine PostgreSQL pada replica menolak perintah tersebut dan secara tegas mengembalikan pesan galat:
    `ERROR: cannot execute INSERT in a read-only transaction`
  * **Analisis Kritis:** Hasil pengujian ini membuktikan secara valid prinsip teoretis utama *Streaming Replication*. Karena direktori data replica dikendalikan penuh oleh alur WAL fisik dari primary, izin transaksi penulisan ditutup total di tingkat kernel PostgreSQL (*Read-Only Standby*). Mekanisme pembatasan ini sangat vital guna mencegah terjadinya ketiadakonsistenan data (*data divergence/drift*) antara node utama dan node cadangan.

#### Langkah 7: Membersihkan Environment Streaming Replication

<img src="img/4.1.4-langkah7.png" width="800" />

* **Pembahasan Detail:**
  Setelah seluruh skenario pengujian replikasi fisik rampung, perintah `dcd` (`docker compose down`) dieksekusi pada terminal host.
  * Docker Compose menghentikan secara halus (*graceful shutdown*) proses mesin PostgreSQL pada kontainer `streaming-replication-postgres_replica-1` dan `streaming-replication-postgres_primary-1`.
  * Selanjutnya, kontainer dan jaringan virtual `streaming-replication_default` dihapus dari sistem.
  * **Analisis Kritis:** Langkah pembersihan ini wajib dilakukan untuk mengosongkan alokasi port host `5432` dan `5433` serta mengembalikan pemanfaatan memori RAM host agar tidak menimbulkan bentrokan saat meluncurkan tumpukan kontainer untuk *Logical Replication*.

## Part 4.2: Logical Replication

### 4.2.1 Konfigurasi & Pengujian Logical Replication

#### Langkah 1: Persiapan File `docker-compose.yaml`

<img src="img/4.2.1-docker-compose.png" width="800" />

* **Pembahasan Detail:**
  Praktikum beralih ke direktori `logical-replication` untuk mengkonfigurasi arsitektur *Logical Replication*. Berkas `docker-compose.yaml` disusun untuk membuat dua instance PostgreSQL yang berdiri sendiri:
  * **`postgres_pub` (Publisher):** Dipetakan pada port host `5432`. Parameter perintah paling vital yang diinjeksikan adalah `wal_level=logical`.
  * **`postgres_sub` (Subscriber):** Dipetakan pada port host `5433` dengan mode pengoperasian PostgreSQL standar.
  * **Analisis Kritis:** Opsi `wal_level=logical` menginstruksikan engine PostgreSQL Publisher untuk menambahkan informasi dekode logis (*logical decoding information*) ke dalam berkas WAL. Informasi tambahan ini memungkinkan plugin dekode PostgreSQL mengekstrak instruksi DML murni (seperti *INSERT tuples*) dari log binary mentah agar dapat dikirimkan dalam format yang dipahami oleh node subscriber independen.

#### Langkah 2: Membuat File Alias `env.sh`

<img src="img/4.2.1-env.png" width="800" />

* **Pembahasan Detail:**
  Berkas `env.sh` disusun ulang untuk mengadaptasi nama kontainer pada proyek *Logical Replication*.
  * Alias `dep` disesuaikan untuk mengarah ke kontainer `logical-replication-postgres_pub-1`.
  * Alias `der` disesuaikan untuk mengarah ke kontainer `logical-replication-postgres_sub-1`.
  * **Analisis Kritis:** Penyesuaian nama kontainer pada variabel alias sangat penting dilakukan agar perintah pengujian tidak menyasar kontainer bekas proyek *Streaming Replication* yang sudah dimatikan, sehingga menjamin kelancaran interaksi CLI selama pengujian logis.

#### Langkah 3: Menyalakan Service & Verifikasi Status

<img src="img/4.2.1-dcu-dps.png" width="800" />

* **Pembahasan Detail:**
  Perintah `source env.sh` dieksekusi dilanjutkan dengan alias `dcu` dan `dps`.
  * Docker Compose secara otomatis mengalokasikan jaringan virtual baru bernama `logical-replication_default`.
  * Dua kontainer otonom `logical-replication-postgres_sub-1` dan `logical-replication-postgres_pub-1` berhasil dinyalakan dan mencapai status `Up About a minute (healthy)`.
  * **Analisis Kritis:** Berbeda dengan replikasi fisik di mana subscriber harus menunggu salinan data fisik `pg_basebackup`, pada replikasi logis kedua kontainer langsung dapat mencapai status `healthy` secara independen sejak detik awal karena masing-masing memiliki direktori basis data yang berdiri sendiri.

#### Langkah 4: Setup Publisher (`postgres_pub`)

<img src="img/4.2.1-publisher-setup.png" width="800" />

* **Pembahasan Detail:**
  Akses dipasangkan ke kontainer Publisher melalui alias `dep`. Tiga instruksi SQL dieksekusi:
  1. `CREATE TABLE users (id SERIAL PRIMARY KEY, name VARCHAR(50));`: Membangun struktur tabel `users` di Publisher.
  2. `CREATE PUBLICATION my_pub FOR TABLE users;`: Mendaftarkan objek publikasi logis bernama `my_pub` yang secara spesifik mengidentifikasi tabel `users` sebagai objek data yang akan didistribusikan.
  3. `INSERT INTO users (name) VALUES ('Budi'), ('Siti');`: Mengisi dua baris record sampel pada Publisher.
  * Respon terminal mengembalikan pesan `CREATE TABLE`, `CREATE PUBLICATION`, dan `INSERT 0 2`.
  * **Analisis Kritis:** Perintah `CREATE PUBLICATION` membuat objek internal yang bertugas menyaring (*filtering*) perubahan data pada tabel `users`. Perubahan pada tabel lain yang tidak mendaftar ke dalam publikasi tidak akan pernah dikirimkan ke jaringan, menegaskan sifat replikasi logis yang selektif.

#### Langkah 5: Setup Subscriber (`postgres_sub`)

<img src="img/4.2.1-subscriber-setup.png" width="800" />

* **Pembahasan Detail:**
  Akses terminal dipindahkan ke kontainer Subscriber melalui alias `der`.
  1. `CREATE TABLE users (id SERIAL PRIMARY KEY, name VARCHAR(50));`: Struktur tabel `users` diciptakan secara manual terlebih dahulu pada Subscriber.
  2. `CREATE SUBSCRIPTION my_sub CONNECTION 'host=postgres_pub port=5432 dbname=zdb user=zuser password=zpass' PUBLICATION my_pub;`: Mengatur ketersambungan langganan logis.
  * Respon terminal mengembalikan notifikasi `NOTICE: created replication slot "my_sub" on publisher` diikuti pesan `CREATE SUBSCRIPTION`.
  * **Analisis Kritis:** Replikasi logis **tidak mentransfer skema tabel (DDL)**. Oleh karena itu, tabel `users` wajib dibuat terlebih dahulu di Subscriber sebelum perintah `CREATE SUBSCRIPTION` dipanggil. Begitu langganan diaktifkan, Subscriber secara otomatis meminta Publisher untuk membuat *logical replication slot* guna menjaga alur dekode logis.

#### Langkah 6: Verifikasi Replikasi Data pada Subscriber

<img src="img/4.2.1-select-subscriber.png" width="800" />

* **Pembahasan Detail:**
  Pemeriksaan hasil sinkronisasi data dilakukan pada node Subscriber (`der`) dengan mengeksekusi kueri `SELECT * FROM users;`.
  * Hasil keluaran menyajikan tabel dengan data yang identik dengan Publisher:
    * `id = 1 | name = Budi`
    * `id = 2 | name = Siti`
  * **Analisis Kritis:** Keberhasilan kueri ini menunjukkan kinerja proses *Initial Data Copy*. Saat pembuatan *subscription* disetujui, worker replikasi pada Subscriber secara otomatis menyalin seluruh snapshot data eksis yang ada pada Publisher sebelum melanjutkan ke alur *streaming* delta perubahan data secara *real-time*.

#### Langkah 7: Pengujian Read-Write & Kendala Conflict Sequence

<img src="img/4.2.1-insert-error.png" width="800" />

* **Pembahasan Detail:**
  Guna membuktikan bahwa Subscriber merupakan node yang bersifat *Read-Write*, dieksekusi instruksi penulisan data lokal secara langsung pada Subscriber: `INSERT INTO users (name) VALUES ('Cici');`.
  * Namun, kueri tersebut ditolak oleh engine dengan pesan galat:
    `ERROR: duplicate key value violates unique constraint "users_pkey"`
    `DETAIL: Key (id)=(1) already exists.`
  * **Analisis Kritis Ketiadaan Replikasi Sequence:** Ini merupakan fenomena teknis paling krusial dalam *Logical Replication*. Replikasi logis **hanya mentransfer nilai tuple baris data, namun tidak mereplikasi nilai pencacah sequence auto-increment (`users_id_seq`)**. Karena data `Budi` (id 1) dan `Siti` (id 2) masuk ke Subscriber melalui alur replikasi logis internal, pointer *sequence* lokal pada Subscriber masih berada pada posisi awal (`1`). Saat pengguna mengeksekusi `INSERT` lokal, sistem mencoba menggenerasi ID otomatis sebesar `1`, yang secara langsung menabrak data `Budi` (id 1) yang sudah ada, sehingga memicu kegagalan *Primary Key constraint*.

#### Langkah 8: Sinkronisasi Sequence & Keberhasilan Read-Write

<img src="img/4.2.1-sequence-success.png" width="800" />

* **Pembahasan Detail:**
  Guna mengatasi permasalahan bentrokan pencacah ID tersebut, dieksekusi langkah perbaikan *sequence* secara manual pada Subscriber:
  1. `SELECT setval('users_id_seq', (SELECT MAX(id) FROM users));`: Perintah ini menghitung nilai ID tertinggi yang ada pada tabel `users` saat ini (yaitu `2`), lalu memaksa pointer `users_id_seq` lokal pada Subscriber agar meloncat ke nilai `2`.
  2. `INSERT INTO users (name) VALUES ('Cici');`: Perintah penulisan lokal dieksekusi ulang. Karena *sequence* telah berada di angka `2`, sistem menggenerasi `id = 3` secara mulus tanpa bentrokan.
  3. `SELECT * FROM users;`: Menampilkan 3 baris data: `Budi` (id 1), `Siti` (id 2), dan `Cici` (id 3).
  * **Analisis Kritis:** Keberhasilan transaksi `INSERT` data `Cici` membuktikan secara sah bahwa node Subscriber pada *Logical Replication* bersifat **Read-Write** penuh. Tidak seperti *Streaming Replication* yang menolak penulisan, Subscriber pada replikasi logis dapat bertindak sebagai basis data operasional mandiri, dengan catatan manajemen kolom *auto-increment* atau *sequence* harus dikelola secara hati-hati oleh pengembang sistem.

## Analisis Perbandingan Komprehensif

Tabel berikut menyajikan pemetaan perbandingan teknis antara *Streaming Replication* dan *Logical Replication* berdasarkan hasil pengujian eksperimental praktikum:

| Parameter Evaluasi | Physical / Streaming Replication | Logical Replication |
| :--- | :--- | :--- |
| **Tingkat Abstraksi Data** | Blok Fisik / Byte-by-Byte (`PGDATA`) | Baris Data / Tuples Logis (`row-level`) |
| **Sifat Node Sekunder** | **Read-Only** (*Hot Standby*) | **Read-Write** (Otonom) |
| **Granularitas Replikasi** | Seluruh Cluster Basis Data (100%) | Selektif per Tabel (`PUBLICATION`) |
| **Transfer Skema (DDL)** | Otomatis direplikasi dari Primary | **Manual** (Skema wajib disiapkan di Subscriber) |
| **Penanganan Sequence** | Otomatis identik (Salinan fisik WAL) | **Harus disesuaikan manual** via `setval()` |
| **Metode Inisialisasi** | Physical Base Backup (`pg_basebackup`) | Initial Table Copy (Otomatis via Subscription) |
| **Kompatibilitas Versi PG** | Wajib versi mayor & OS yang identik | Mendukung beda versi mayor & OS heterogen |
| **Overhead CPU & Memory** | Sangat Rendah (Penyalinan mentah WAL) | Sedikit Lebih Tinggi (Proses *Logical Decoding*) |
| **Skenario Penggunaan Utama**| • *Disaster Recovery* (DR)<br>• *High Availability* (HA)<br>• *Read Scaling Load Balancing* | • *Zero-Downtime Major Version Upgrade*<br>• *Data Warehousing / Analytics Aggregation*<br>• Multi-Branch Local Write System |

## Kesimpulan

Berdasarkan seluruh rangkaian eksperimen praktikum PostgreSQL Replication yang telah dilaksanakan, dapat ditarik beberapa kesimpulan mendasar:

1. **Streaming Replication (Physical Replication):**
   * Beroperasi pada tingkatan fisik paling dasar (*byte-by-byte*) dengan menyalurkan berkas log WAL secara langsung dari node Primary ke Replica.
   * Mengatur node Replica menjadi *Hot Standby* yang bersifat murni **Read-Only**, sehingga menjamin tingkat konsistensi data fisik yang mutlak tanpa risiko *data divergence*.
   * Membutuhkan inisialisasi awal berbasis `pg_basebackup` serta menuntut keseragaman versi mesin PostgreSQL dan arsitektur sistem operasi.
   * Menjadi solusi terbaik untuk kebutuhan *High Availability* (HA), pemulihan bencana (*Disaster Recovery*), dan pemisahan beban kueri pembacaan (*Read Scaling*).

2. **Logical Replication:**
   * Beroperasi pada tingkatan objek data atau baris (*row-level*) memanfaatkan arsitektur *Publish-Subscribe* dan fitur *Logical Decoding*.
   * Mengatur node Subscriber menjadi basis data mandiri yang bersifat **Read-Write**, memungkinkan eksekusi transaksi manipulasi data lokal secara independen.
   * Menawarkan fleksibilitas tinggi berupa replikasi selektif per tabel dan kompatibilitas lintas versi mayor PostgreSQL, namun mensyaratkan penanganan manual pada pencacah *sequence* (`setval`) untuk mencegah konflik *Primary Key*.
   * Menjadi solusi ideal untuk skenario migrasi versi basis data tanpa *downtime*, integrasi data antar-sistem heterogen, serta pemrosesan data lokal di kantor cabang.
